## 1. Project purpose and operating context

Build and maintain a reliable, low-cost LPG distribution operations system for Samruddhi Gas Agency. The agency serves a large consumer base (approximately 11,000 consumers was previously stated) and uses HPCL systems for official booking/delivery records.

The system is intended to make daily office and delivery work easier without requiring the agency owner to understand programming or perform repeated technical steps.

### Core goals
- Office dashboard for consumer, delivery, GPS, and route operations.
- Delivery staff mobile app with simple assigned-booking workflow.
- Consumer location-capture link/form that records a customer's location with consent.
- Accurate GPS capture in practical field conditions, without making delivery staff retry endlessly.
- Securely store and manage consumer coordinates; distinguish unreviewed from office-approved pins.
- Support offline/poor-network operation where designed, and safely sync pending work.
- Make delivery routes easier for new delivery staff and reduce travel time and operating cost.
- Preserve existing working data and features during every change.
- Use HPCL records as the official source for HPCL delivery confirmation. This project is an operational aid, not a replacement for HPCL's official system.

### Owner's working preferences (mandatory)
- The owner is not a technical person. The assistant/developer should do the technical work end-to-end.
- Do not repeatedly ask the owner to run commands, edit source files, inspect logs, or perform avoidable technical steps.
- Ask only for information or a real-world test that cannot safely be completed remotely.
- Do not repeat already completed work. Inspect the current repository and deployed services first.
- Make small, controlled, reversible changes. Preserve known-good behavior and existing records.
- Explain results in plain language: what changed, what was checked, what still needs a real phone/office test.
- Never say “fixed”, “deployed”, “working”, or “verified” unless the corresponding checks actually passed.

## 4. GPS capture rules and current implementation

GPS reliability is a major project requirement. Delivery staff need to capture locations while moving through their assigned area, and customers should be able to share a location without repeated failed attempts.

### Consumer LocationCapture — latest implementation
Source: root `index.html`; backend action: `gps_link_capture` in `lpg-api`.

Latest change committed as:
- Commit: `40385802e0f9c2965901e6f50b9b293df6d4820b`
- Commit URL: https://github.com/samruddhigas/locate/commit/40385802e0f9c2965901e6f50b9b293df6d4820b
- Change: continuous high-accuracy watch and best-fix selection; early map/pin step when a good fix is available; after a wait, fallback to the best fresh fix within 30 metres; one valid reading can be submitted rather than forcing five readings and a tight spread.
- Server-side consumer capture validation was changed to accept a fresh, valid reading with accuracy greater than 0 and no worse than 30 metres, while retaining secure one-time-link checks, approved-pin protection, the maximum pin-offset rule, and office review/approval workflow.

**Important:** The 30 m value is an acceptance ceiling/fallback, not a promise that every capture will be within 7 m. Actual accuracy depends on phone hardware, Android location settings, GPS visibility, permissions, network assistance, and surroundings. The interface should show the reported accuracy and must not misrepresent it.

### DeliveryApp — current source observations
- `deliveryapp/index.html` loads `app.js` and `app.css`.
- The page includes a GPS-only consumer search, separate from assigned bookings.
- The interface explains that marking a delivery done attempts GPS automatically; if no usable fix is available, delivery completion can still be saved and GPS can be captured later using consumer search.
- `deliveryapp/sw.js` cache was bumped to `samruddhi-delivery-v15` so installed clients can receive changed assets.
- The standalone app stores queued delivery/GPS work locally and keeps the signed session token in `sessionStorage`, while offline work data is kept in local storage. Audit security and expiry behavior before changing.
- The Dashboard also contains an embedded DeliveryApp generator/implementation. It must be checked against the standalone app before claiming GPS behavior is identical.

Cache update commit:
- `bd31411437f8b7370339b7607b064f7a24d39056`
- https://github.com/samruddhigas/locate/commit/bd31411437f8b7370339b7607b064f7a24d39056

### GPS acceptance principles for future changes
1. Use `watchPosition` with high accuracy where supported; retain the best fresh fix instead of requiring an arbitrary fixed number of readings.
2. Use sensible timeout/fallback behavior. Never keep delivery staff trapped in endless retries.
3. Show accuracy in metres, capture age, and whether the reading is acceptable.
4. Reject stale, invalid, zero/negative, or obviously impossible coordinates.
5. Keep consumer capture, delivery capture, manual office capture, and route approval as distinct modes with server-side authorization.
6. A “Mark Done” action should attempt GPS automatically if no acceptable location exists, but should not silently claim GPS was captured when it failed.
7. Queue offline work safely and visibly; never discard unsynced delivery or GPS data on logout or refresh.
8. Test actual Android phones in open sky, beside buildings, indoors, while walking, and under weak network conditions.
9. Never promise a fixed 7 m result. Record measured results from real tests.
10. Do not weaken security or approval rules merely to make GPS acceptance easier.

## 9. Known issues, limitations, and risks

These are known or unresolved at handover time. Do not hide them or silently move them to “completed”.

1. **Real-world GPS accuracy is not yet proven.** The code now allows a best fresh fix up to 30 m, but actual accuracy under 7 m has not been demonstrated by documented field tests.
2. **Hosted pages were not live-verified.** Repository commits and Supabase function versions are confirmed; GitHub Pages delivery and browser cache behavior still need device checks.
3. **Standalone and embedded DeliveryApp implementations coexist.** The Dashboard embeds/generates a DeliveryApp implementation while `deliveryapp/` contains a separate PWA. They can drift unless parity is tested.
4. **Delivery completion can be saved when GPS is unavailable.** This is intentional to avoid blocking field work, but the interface and office reporting must clearly distinguish “delivery marked done” from “GPS saved”.
5. **Route publishing is not confirmed end-to-end.** The standalone app's interface currently indicates that office-published route ordering is not yet connected/available in that app's workflow; investigate and reconcile with Dashboard route features.
6. **Some Dashboard capabilities were previously noted as disabled or requiring manual review**, including advanced security controls and backup/restore. Re-inspect the current source before stating their present status.
7. **No full production acceptance test has been completed in this handover.** Source/deployment verification must not be confused with a successful office-and-delivery-day trial.
8. **`verify_jwt=false` is configured on both listed Edge Functions.** This is not automatically a vulnerability if the function validates its own session/authentication, but every public action must be audited for authorization, input validation, rate limiting where appropriate, and data exposure.
9. **A publishable/anon key is present in the standalone DeliveryApp source.** Treat it as public by design; rely on RLS/server-side authorization, never on hiding this key.
10. **Browser geolocation depends on secure context, user permission, Android settings, hardware, and environmental conditions.** No software change can guarantee a particular accuracy in every situation.

## 18. 26 November 2026 — Repeated-delivery location verification and deviation exceptions

**Code baseline for this update:** `9c0d114149783393c7ee7367a5d799ceb12d57b6` (the handover commit follows).  
**Production backend:** `lpg-api` v49 ACTIVE; `deliveryapp` v3 ACTIVE.  
**Standalone DeliveryApp service-worker cache:** `samruddhi-delivery-v17`.

### Implemented in production backend and source

- Added `lpg_gps_temporary`, `lpg_delivery_location_observations`, and `lpg_delivery_location_exceptions`. Existing `lpg_gps` office-approved coordinates remain the permanent source and are not overwritten by delivery observations.
- Every completed booking can contribute one fresh visit observation, tied to the assigned delivery account and booking key. Retries are idempotent.
- Multiple bookings for the same consumer on the same local calendar day count as **one physical visit**. A same-day repeat does not increase the verification count.
- When no permanent office-approved pin exists:
  1. First valid visit creates a candidate.
  2. Second consistent visit on a different local calendar day, within 20 metres of the temporary cluster and with reported accuracy no worse than 30 metres, makes it provisional.
  3. Third consistent visit on a different local calendar day makes it **temporary_approved** and route-eligible.
- A visit more than 20 metres from the temporary cluster is recorded as an outlier exception and does not move the temporary pin.
- When a permanent office-approved pin exists, it always takes precedence:
  - Up to 30 metres: matched.
  - More than 30 metres and up to 50 metres: warning exception.
  - More than 50 metres: deviation exception.
- The authenticated office API exposes the exception queue and allows admin/staff to resolve an exception with a review note.
- Office GPS sync keeps temporary pins in a separate state from permanent approvals. The route planner and route publisher can use a 3-visit temporary pin when no permanent approved pin exists; they do not promote it to a permanent master pin.
- Delivery completion remains possible when GPS is unavailable. A missing or weak fix is recorded as such; the app does not falsely claim GPS verification or block a real-world handover.
- If a completion was saved but its location check failed transiently, a retry can finish the location check without duplicating the delivery completion.

### GPS capture responsiveness

- Standalone DeliveryApp, Dashboard-generated DeliveryApp, and the customer capture page now accept the first fresh usable fix at 30 metres or better instead of waiting for a 10-metre fix.
- GPS capture uses a short bounded wait (up to about 5 seconds), permits a recent cached reading (up to 15 seconds old), and continues to show the actual reported accuracy.
- Mark Done obtains a new visit reading for that delivery; an earlier mapping capture is not reused as evidence for a later delivery.
- The delivery app and Dashboard retain the draggable entrance pin, tap-to-place, road/satellite map layers, and the 500-metre pin-offset guard. Raw GPS coordinates and the selected entrance pin remain distinct.
- **Accuracy limitation:** no browser app can guarantee a 7-metre fix on every phone or at every building. If a fresh reading does not meet the 30-metre acceptance limit within the short wait, the app reports the actual limitation and can still save the delivery without claiming a verified location.
- The map uses Leaflet with CARTO/OpenStreetMap road tiles and Esri satellite imagery. Google Maps is used for navigation links; these are not Google Maps map tiles. Actual Google Maps JavaScript tiles would require an authorized Google Maps API key and applicable billing.
